# Findings: what the AI got wrong

> One row per finding. "How found" is one of: acceptance test, conformance
> check, code review, measurement, other (say what). Link the commit that
> fixed it.

## Variant A

| # | What the AI produced | Why it is wrong or risky | How found | Fix (commit) |
|---|----------------------|--------------------------|-----------|--------------|
| 1 | The undo receipts are keyed only by the client's `X-Request-Id`, exactly as our design says, and `sales` does not check for a repeated id ([`common/db.py`](../variant-a/common/db.py)). The gap is in our design; the AI's mistake is that it did not flag it, although AGENTS.md tells it to ask when the design leaves a decision open. | If a client sends the same checkout twice with the same id, two sales are saved, but stock and points change only once. This breaks the contract ("the sale reduces the stock of every line"). | Code review, then a manual test: the same checkout sent twice gave sales 16 and 17, while stock dropped by 1 instead of 2 | needed, not done yet |
| 2 | Undoing a stock give-back (return) subtracts the stock without checking it ([`inventory/app.py`](../variant-a/inventory/app.py)). | If the returned item is sold before the return fails, the undo pushes stock below 0. Our design says stock never goes below 0. | Code review | not fixed: needs three requests to overlap, accepted as a known gap |
| 3 | The 2 s limit between services is set as `httpx.Client(timeout=2)` ([`common/calllog.py`](../variant-a/common/calllog.py)). | httpx applies the 2 s to each phase of a call, not to the whole call, so a slow service can take longer. Our 20 s gateway limit assumes 2 s per call. | Code review | not fixed: with our small answers a call still fails after about 2 s |
| 4 | When closing a register, an error from `sales` is passed on as it is, and a broken `200` answer does not reopen the session ([`stores/app.py`](../variant-a/stores/app.py)). | The design says: if sales fails, reopen the session and answer `503`. The main case (sales stopped) works; only these rare cases differ. | Code review, plus a manual test with `sales` stopped | not fixed: rare, the main case works as designed |

## Variant B

| # | What the AI produced | Why it is wrong or risky | How found | Fix (commit) |
|---|----------------------|--------------------------|-----------|--------------|
| 1 | reporting recorded each ledger entry with an `applied_steps` receipt keyed on (`X-Request-Id`, step), and answered "already done" for a known key (`reporting/app.py`, `record_sale`, `record_refund`). This follows our design to the letter. | The contract lets the client choose `X-Request-Id`. Two sales sent with the same id (a till that retries, a buggy client) both commit in till, but reporting finds the receipt of the first and answers `200` for the second without writing it; till marks the row delivered. The Z-report then counts both sales and the sales report one, with no error and nothing left in the outbox: exactly the silent mismatch C5 is about. The gap is in our spec; the agent did not question it. | code review (the tests cannot see it: `tests/pos.py` sends a new id with every request) | needed, not done yet |
| 2 | `earn_points` in customers has the same receipt key (`X-Request-Id`, `earn_points`). | A second sale with a reused id gets `reward_points_earned` of the first sale in its body, but the points are not added to the customer. Wrong data, but visible and limited to loyalty points. | code review | needed, not done yet |
| 3 | `common/db.py` opens a new MariaDB connection for every `transaction()`; there is no pool. A checkout with a customer opens four connections in till alone (checks, write, outbox read, outbox mark) plus one in customers and one in reporting. | Adds connection setup to every step and inflates checkout latency (C3). Same code in both variants, so the comparison stays fair, but the absolute numbers are worse than they need to be. | code review | not fixed: same in both variants, changing it in one would bias C3 |
| 4 | Calls between services use `httpx` with `timeout=2`; the gateway with `timeout=20`. | In `httpx` this is a limit per phase (connect, write, read, pool), not for the whole call. The design's "2 s per call" and the worst-case budget of 16 s behind the gateway's 20 s are therefore not hard limits. Low risk with small JSON answers. | code review | not fixed: with our small answers a call still fails after about 2 s |
| 5 | `POST /internal/undo` answers `422` for an unknown step and `500` after three deadlocks. | The design says an undo always answers `200`. The agent listed this deviation itself under "Decisions taken by the agent". | code review of the agent's own notes | not fixed: only happens with a programming error or a failing database |
