# Findings: what the AI got wrong

> One row per finding. "How found" is one of: acceptance test, conformance
> check, code review, measurement, other (say what). Link the commit that
> fixed it.
>
> Numbering: A… for variant A, B… for variant B, counted on across both
> versions, so that every number names one finding (`docs/design.md` refers to
> B1).

## Version 1

### Variant A

| # | What the AI produced | Why it is wrong or risky | How found | Fix (commit) |
|---|----------------------|--------------------------|-----------|--------------|
| A1 | The undo receipts are keyed only by the client's `X-Request-Id`, exactly as our design says, and `sales` does not check for a repeated id ([`common/db.py`](../variant-a/common/db.py)). The gap is in our design; the AI's mistake is that it did not flag it, although AGENTS.md tells it to ask when the design leaves a decision open. | If a client sends the same checkout twice with the same id, two sales are saved, but stock and points change only once. This breaks the contract ("the sale reduces the stock of every line"). | Code review, then a manual test: the same checkout sent twice gave sales 16 and 17, while stock dropped by 1 instead of 2 | Fixed. The undo receipts are no longer keyed on the X-Request-Id the client sends. They use a new header. The change is in common/calllog.py and common/db.py, and the design was updated to match. Commit `34cd95d`. |
| A2 | Undoing a stock give-back (return) subtracts the stock without checking it ([`inventory/app.py`](../variant-a/inventory/app.py)). | If the returned item is sold before the return fails, the undo pushes stock below 0. Our design says stock never goes below 0. | Code review | not fixed: needs three requests to overlap, accepted as a known gap |
| A3 | The 2 s limit between services is set as `httpx.Client(timeout=2)` ([`common/calllog.py`](../variant-a/common/calllog.py)). | httpx applies the 2 s to each phase of a call, not to the whole call, so a slow service can take longer. Our 20 s gateway limit assumes 2 s per call. | Code review | not fixed: with our small answers a call still fails after about 2 s |
| A4 | When closing a register, an error from `sales` is passed on as it is, and a broken `200` answer does not reopen the session ([`stores/app.py`](../variant-a/stores/app.py)). | The design says: if sales fails, reopen the session and answer `503`. The main case (sales stopped) works; only these rare cases differ. | Code review, plus a manual test with `sales` stopped | not fixed: rare, the main case works as designed |

### Variant B

| # | What the AI produced | Why it is wrong or risky | How found | Fix (commit) |
|---|----------------------|--------------------------|-----------|--------------|
| B1 | reporting recorded each ledger entry with an `applied_steps` receipt keyed on (`X-Request-Id`, step), and answered "already done" for a known key (`reporting/app.py`, `record_sale`, `record_refund`). This follows our design to the letter. | The contract lets the client choose `X-Request-Id`. Two sales sent with the same id (a till that retries, a buggy client) both commit in till, but reporting finds the receipt of the first and answers `200` for the second without writing it; till marks the row delivered. The Z-report then counts both sales and the sales report one, with no error and nothing left in the outbox: exactly the silent mismatch C5 is about. The gap is in our spec; the agent did not question it. | code review (the tests cannot see it: `tests/pos.py` sends a new id with every request) | Fixed. Reporting now records each ledger entry once per sale ID or return ID, so a repeated delivery changes nothing, and a different sale is never mistaken for one already recorded. Reporting no longer keeps receipts and has no undo. The change is in reporting/app.py, and the design was updated to match. Commit `34cd95d`. |
| B2 | `earn_points` in customers has the same receipt key (`X-Request-Id`, `earn_points`). | A second sale with a reused id gets `reward_points_earned` of the first sale in its body, but the points are not added to the customer. Wrong data, but visible and limited to loyalty points. | code review | Fixed by the same change as A1: receipts are keyed on a step key that the leader creates, not on the client’s request id. Till’s background work also gets a fresh key each time it calls another service. Commit `34cd95d`. |
| B3 | `common/db.py` opens a new MariaDB connection for every `transaction()`; there is no pool. A checkout with a customer opens four connections in till alone (checks, write, outbox read, outbox mark) plus one in customers and one in reporting. | Adds connection setup to every step and inflates checkout latency (C3). Same code in both variants, so the comparison stays fair, but the absolute numbers are worse than they need to be. | code review | not fixed: same in both variants, changing it in one would bias C3 |
| B4 | Calls between services use `httpx` with `timeout=2`; the gateway with `timeout=20`. | In `httpx` this is a limit per phase (connect, write, read, pool), not for the whole call. The design's "2 s per call" and the worst-case budget of 16 s behind the gateway's 20 s are therefore not hard limits. Low risk with small JSON answers. | code review | not fixed: with our small answers a call still fails after about 2 s |
| B5 | `POST /internal/undo` answers `422` for an unknown step and `500` after three deadlocks. | The design says an undo always answers `200`. The agent listed this deviation itself under "Decisions taken by the agent". | code review of the agent's own notes | not fixed: only happens with a programming error or a failing database |

## Version 2 (CR1, CR2)

### Variant A

| # | What the AI produced | Why it is wrong or risky | How found | Fix (commit)                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
|---|----------------------|--------------------------|-----------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| A5 | The v2 schema changes exist only in `CREATE TABLE IF NOT EXISTS` (new columns `ticket_system.tier`, `.points_rate`, `item_list.vat_rate`; new tables `vat_table`, `vat_category`, `ticket_vat`), and the VAT rates are written only by `fill()`, which runs only on an empty database ([`sales/app.py`](../variant-a/sales/app.py)). The agent's own decision note says `item_list.vat_rate` got a default "so that the column could be added to the legacy table", but no code adds it. | A running v1 stack that is upgraded to the v2 code without wiping its data keeps its old tables: no VAT rates, no new columns. Every sale then fails with `500`, while all health checks stay green. The tests cannot see it, because `make up-a` always starts from empty databases; in a store the upgrade would stop every till. | Code review, then a test: the v1 code (from tag `v1`) started, one sale; then `docker compose up -d --build` with the v2 code, without `-v`: `POST /sales` answered `500` (`'NoneType' object is not subscriptable`, `vat_table` empty). | Fixed. sales now runs a migration step at every start: it adds the new columns if they are missing and writes the VAT rates if they are missing, so an upgraded v1 database works and a v2 database is left as it is. Sales made under v1 keep their v1 refund and give back points at 1 per CHF. Checked by upgrading a running v1 stack with a customer sale to v2 without a reset: new sales, a return of the old sale and a restart all worked. Commit: 5cc93b3 |

### Variant B

| # | What the AI produced | Why it is wrong or risky | How found | Fix (commit)                                                                                                                                                                                                                                                                                                                                                                                                                                             |
|---|----------------------|--------------------------|-----------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| B6 | The same as A5 in till: new columns and the `vat_rates` rows exist only in a fresh database ([`till/app.py`](../variant-b/till/app.py)). In addition, `sales.tax_rate` is replaced by `sales.tier` in the same column position, so a v1 `sales` table cannot take a v2 sale at all. | As A5: after an upgrade without a reset, every sale fails with `500` and till still reports healthy. | Code review, then the same upgrade test as A5: `POST /sales` answered `500` (`Unknown column 'category'`); `vat_rates` had 0 rows and `sales` still had `tax_rate` and no `tier`. | Fixed. till runs the same kind of migration step at every start: it adds the new columns, writes the VAT rates and fills in each product’s category from the seed. sales.tax_rate is kept and written as 0, as in variant A. A return of a sale made under v1 takes back 1 point per CHF and does not change the spend. Remaining limit: after an upgrade, spend counts only sales from v2 on. Checked with the same upgrade test as A5. Commit: 5cc93b3 |
| B7 | On a return of a customer's sale, till opens its own database transaction before it calls `take_back_points` in customers (`with Steps() as steps, transaction() as cur:` in [`till/app.py`](../variant-b/till/app.py)). The design says: checks, then `take_back_points`, then till's own transaction. The agent chose this so that the v1 block keeps its indentation and fewer lines change in `make impact`, and recorded it as a decision. | Every such return holds a till-db connection while it waits for customers, up to the 2 s timeout. If customers is slow, these connections pile up; MariaDB allows 151, and after that every request in till fails, checkout included. A slow loyalty service could stop the tills, against C1 and the main reason for the cut (connection management, one of the disintegrators from the course). The gain is a few changed lines, which only count as the C2 tie-breaker. | Code review, then a test: customers paused (`docker pause`), five returns of a customer's sale sent at once: till-db had 5 open connections from till (0 before), released only after the 2 s timeouts. | Fixed. On a return, till now takes back the points before it opens its own transaction, as the design says, so no database connection is held while it waits for customers. Checked again with customers paused: five waiting returns held no till-db connections (five before the fix). Commit: 5cc93b3                                                                                                                                                 |
